# Bout-to-Bout

A free, mobile-first folkstyle wrestling tournament wait-time calculator. Bout-to-Bout estimates how long it may take before a wrestler's next bout is called. It is **not** live tournament tracking; official tournament calls always take priority.

## What changed in v2.0

- Added a **multi-server queueing model**: active mats are treated as parallel servers processing bouts.
- Added **Monte Carlo simulation** rather than assuming every bout lasts exactly the average time.
- Shows a median estimate plus a **10th–90th percentile likely range**.
- Keeps the original deterministic formula as a visible baseline for comparison.
- Added an anonymous **user feedback form** with optional actual wait-time reporting.
- Feedback rows can be stored in Supabase so prediction error can later be analyzed against real tournament data.

## Statistical model

### Deterministic baseline

When the assigned-mat queue is unknown:

```text
baseline = (nextBout - currentBout) / activeMats * avgBoutTime + expectedDelay
```

When `Bouts Ahead on Your Mat` is supplied:

```text
baseline = boutsAhead * avgBoutTime + expectedDelay
```

### Queueing + Monte Carlo estimate

The stochastic model treats each active mat as a parallel server. Bout service times are sampled from a positive lognormal distribution whose mean equals the user's selected average bout time. The current bouts on each mat are given an unknown residual service time, then queued bouts are assigned to whichever mat becomes available first.

The simulation runs 800–4,000 trials depending on queue size and reports:

- **Estimated wait:** median simulated wait (50th percentile)
- **Likely range:** 10th–90th percentile simulated wait
- **Baseline:** the deterministic formula above

The current coefficient of variation is a modeling assumption (`0.45`) in `src/lib/calc.ts`. It should eventually be calibrated or replaced with an empirical bout-duration distribution from real tournament data. Until then, do **not** describe the distribution as empirically validated.

## Feedback and model validation

The feedback form can collect:

- feedback category
- optional free-text feedback
- optional actual wait time
- the calculator inputs used for that prediction
- predicted wait, baseline wait, and predicted interval
- model version

No name or email is required by the app.

Once enough real wait-time reports are collected, the model can be evaluated with metrics such as Mean Absolute Error (MAE):

```text
MAE = mean(abs(predictedWait - actualWait))
```

This creates a clean development path: baseline model → stochastic model → real-user validation → model calibration.

## Configure Supabase feedback

The calculator itself works without a backend. Supabase is only required for submitting feedback.

### 1. Create a Supabase project

Create a project at Supabase, then open the SQL editor and run:

```sql
create table if not exists public.feedback (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  category text not null check (category in ('accuracy', 'feature', 'bug', 'other')),
  message text,
  actual_wait numeric,
  predicted_wait numeric not null,
  likely_low numeric not null,
  likely_high numeric not null,
  baseline_wait numeric not null,
  current_bout integer not null,
  next_bout integer not null,
  active_mats integer not null,
  avg_bout_time numeric not null,
  expected_delay numeric not null,
  bouts_ahead integer,
  estimate_mode text not null,
  model_version text not null
);

alter table public.feedback enable row level security;

create policy "anonymous feedback insert"
on public.feedback
for insert
to anon
with check (
  char_length(coalesce(message, '')) <= 1000
  and (actual_wait is null or (actual_wait >= 0 and actual_wait <= 1440))
  and current_bout >= 0
  and next_bout >= 0
  and active_mats between 1 and 100
  and avg_bout_time between 0.25 and 60
);
```

This policy allows anonymous visitors to **insert** feedback but does not grant them permission to read the table.

### 2. Add local environment variables

Copy `.env.example` to `.env.local` and fill in the browser-safe Supabase values:

```text
VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_KEY
```

Use the Supabase **anon/publishable** key only. Never put a service-role key in a Vite environment variable or public repository.

Restart Vite after changing environment variables.

### 3. Add deployment secrets/variables

If deploying with GitHub Actions, Vite needs the two values at build time. Add repository secrets named:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

Then ensure the deploy workflow exposes them to the build step. The included workflow has placeholders for these secrets.

If the feedback variables are absent, the calculator still works; the feedback submit button is disabled and a configuration notice is shown.

## Deploy to GitHub Pages

1. Create a public GitHub repository, e.g. `bout-to-bout`.
2. Upload the contents of this folder to the repository root. Keep `.github/workflows/deploy.yml` and `package-lock.json`.
3. Do not upload `node_modules` or `.env.local`.
4. In **Settings → Pages → Build and deployment**, set Source to **GitHub Actions**.
5. Push to `main` and watch the Actions tab.

The site can also be attached to a custom domain. Domain configuration does not change the calculation model.
